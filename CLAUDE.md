# CLAUDE.md

Userscript for [war.app](https://war.app) (formerly Warzone), run through Tampermonkey. The whole script is the single file `Tidy_up_your_Dashboard.user.js`. There is no build step: the file in the repo is exactly what users install.

## Commands

```bash
npm install        # dev dependencies, only needed for tests
npm test           # node --test test/
npm run check      # syntax check of the userscript
```

To try changes on the live site, reinstall the script in Tampermonkey from the local file or from the raw GitHub URL. `QA.md` is the manual checklist for the live site; run it before a release and add a row when a feature adds visible UI.

## How the script is put together

- **Header:** `@grant none`, so the script runs in the page context. The site's own globals (`$.cookie`, `wljs_WaitDialogJS`, `CreateModal`, Bootstrap's `.modal()`) are available. Switching to any `GM_*` grant sandboxes the script and breaks these.
- **Two jQuerys:** `$` is the site's jQuery, which has the cookie plugin. `$$$` is the `@require`d jQuery 1.11.2 plus jQuery UI, used for the log dialog. DataTables is attached to `$$$`, so call it as `$$$(...).DataTable()`. Never reassign `window.$` or call `noConflict` on the site's jQuery: war.app's pages, the cookie plugin and Bootstrap depend on it.
- **Startup flow:** `DOM_ContentReady()` starts `loadPlayerData()` and runs a list of page features through `runFeatures()`. It then calls `Database.init()`, whose callback runs the menu setup, `checkVersion()` and `databaseReady()`, which is a second feature list for settings-driven features. The lists are built by `pageFeatures()`, `mainFeatures()` and `maakFeatures()`. Each feature is `{ name, section?, match?, run }` and runs in its own try/catch. Add new features as entries pointing at named top-level functions, not as inline blocks. List order is execution order. A feature with a `section` gets a switch in the settings menu's Features part. Its `name` is shown to users and is the key in the stored disabled list, so don't rename it casually. The disabled list lives in the `disabledFeatures` setting and is mirrored to `localStorage` (`DISABLED_FEATURES_KEY`), because page features run before IndexedDB opens.
- **Page routing:** done with the `pageIs*()` helpers, which match the path of `location.href` on any host; `@match` decides which hosts the script runs on.
- **Domains:** nothing hard-codes the site's domain. Links are relative or built from the page (`$a.prop("href")`), page titles are trimmed with the site's own `og:site_name` (`stripSiteSuffix()`), and bookmarks saved on any host in `SITE_HOSTS` render as relative links (`siteRelativeUrl()`). warzone.com and warlight.net only redirect to war.app now, so `@match` lists war.app alone; the old domains stay in `SITE_HOSTS` for old bookmarks. If war.app moves to a new domain, add an `@match` line and add the domain to `SITE_HOSTS`, nothing else. IndexedDB and cookies are per origin, so users carry settings to a new domain with Export / Import.
- **Player data:** `loadPlayerData()` returns a jQuery promise, stored as `window.playerDataReady`. Anything that reads `WlPlayer` must wait on it. It rejects when the user is logged out.
- **Storage:** IndexedDB `TidyUpYourDashboard_v3`, wrapped by `window.Database` from `setupDatabase()`. Every method takes an optional callback and also returns a Promise; failures and callback exceptions are logged. Settings are cached at `init`, and `readIndex` on the Settings name index is served from the cache. Writes update the cache when issued, and callbacks still run asynchronously. Tables are listed in `Database.Table`; only `Database.Exports` tables are included in settings export and import. Player data is cached in the `muli_wl_player` cookie for 1 hour.
- **Third-party services:** maak.ch (proxy and API), www.warlight-mtl.com (the Multi-Template Ladder, MTL, formerly called MDL; the bare `warlight-mtl.com` host also works), communitylevels.online. Any of these can be down, so every request needs a `.fail()` handler. maak.ch and warlight-mtl.com send no CORS headers, so under `@grant none` they can only be reached through maak.ch's JSONP endpoints, which run as code on war.app. Everything that calls maak.ch is reachable only through `setupMaakFeatures()`, behind the `useMaakServices` setting (off by default), and a test enforces this. awp.wl-stats.com and custom.wl-stats.com (run by this fork's maintainer) send CORS headers for `https://war.app` and its subdomains, so the script reads their `/api/v1/` JSON directly with `fetchWlStats()`, which keeps answers in `sessionStorage` (an hour by default, 10 minutes for `/api/v1/series`) and resolves a 404 with `null`. Profile boxes from these sites go through `placeProfileBox()`, which keeps them in a fixed order below the private notes. `loadCommunityData()` loads the AWP ranking and the custom series side by side for the Ladders and Community Events pages; custom's times have no zone and are UTC (`parseUtcTime()`). Prefer war.app's own pages for new data, as `fetchDashboard()` and `parseLevelPage()` do. They're same-origin, so parse them with `DOMParser`, never `$(html)`, so their scripts and images stay inert.
- **Game refresh event:** `refreshGameTable()` triggers `tuyd:gamesRefreshed` on `document` with the table selector after each refresh, including the 5-minute background check from `setupTurnAlerts()`. Hook into it rather than wrapping the refresh functions. Most other pages (tournaments, ladders, clan pages) are now drawn client-side by war.app as absolutely positioned `ujs_*` elements and have no `#MainSiteContent`. war.app also switches between these views without a page load (e.g. tournaments list → tournament), redraws them, and numbers repeated ids (`ujs_CreatorLabel_2_tmp`). So features for these views watch the page with a `MutationObserver` and re-check each time (`whileOnTournament()`), add their elements only if missing, look elements up with `ujsElement()`, and don't insert into war.app's flow (`tournamentInfoSlot()`). The Ladders panel (`setupCommunityLadders()`) follows the same rules: it hangs below the dialog's background box inside war.app's clipping `ujs_Viewport` and sizes its own scrolling to what's left of it. Where an addition only fits at some widths, a CSS container query on the element it sits in decides, not a viewport media query: war.app re-lays out its scenes at its own pace and widths. Anything clickable needs `pointer-events: auto`, since war.app's panels often have `pointer-events: none`. war.app's own Filter button (`#MyGamesFilterBtn`) re-draws My Games in place without this event; a feature that must follow every re-draw observes the table instead, pausing the observer while it changes rows, as `setupBootTimeSort()` does. A My Games row is your turn when it contains a span whose text starts with "Your turn". After replacing rows, `refreshGameTable()` copies the fresh `#AllOpenGamesData` into the page and re-runs war.app's exported `WL_MPDashInit` (`rerunDashboardInit()`), which re-adds the My Games footer and the Open Games "Show more" row.

## Tests

`test/harness.js` parses the userscript with acorn and evaluates individual top-level function declarations in a `vm` sandbox. Loading the whole file would run page setup. Each test passes in only the globals the function under test needs. Common ones are `$` (npm jQuery 1.11.2 bound to a jsdom window, via `createDom()` and `domGlobals()`), `log`, `Database` and `location`.

- `test/startup.test.js` checks statically that every called or feature-registered function exists. If it flags a new site or browser global, add that name to its allowlist.
- A function becomes testable once it is a **top-level `function` declaration**. Inline logic in `databaseReady()` or `DOM_ContentReady()` has to be extracted first, as was done with `setupBlacklistCounter()`.
- Values created in the sandbox come from another realm. Copy arrays with `Array.from` or a JSON round-trip before using `deepStrictEqual`.
- jsdom has no layout. The harness patches `offsetWidth` so jQuery's `:visible` respects `display: none`.

## Conventions

- When bumping the version, update `@version`, the `GM_info` fallback near the top of the script, and the version line in `README.md` together. A test checks that they match.
- `@downloadURL` and `@updateURL` must point at this repo's raw file, not Greasy Fork. Otherwise upstream releases overwrite this fork.
- Escape third-party and user-supplied strings with `htmlEscape()` before putting them into HTML. URLs from outside (API data, bookmarks) go through `htmlEscape(safeUrl(url))`; `safeUrl` allows only `http(s)://` and same-site `/` paths. `test/security.test.js` covers each renderer with an injection payload, so add a case there when adding a new one.
- Every `@require` must carry a `#sha256-` hash. A test enforces this.
- `ROADMAP.md` tracks planned work. Tick items off there when they land.
