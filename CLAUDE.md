# CLAUDE.md

Userscript for [war.app](https://war.app) (formerly Warzone), run through Tampermonkey. The code lives in `src/`, and `tools/build.js` joins it into `Tidy_up_your_Dashboard.user.js`, the single file users install. That file is committed, because `@downloadURL` serves it straight from `main`, so never edit it by hand: edit `src/`, run `npm run build`, and commit both.

## Commands

```bash
npm install        # dev dependencies, only needed for tests
npm run build      # joins src/ into the .user.js
npm test           # node --test test/
npm run check      # syntax check of the userscript
```

To try changes on the live site, build, then reinstall the script in Tampermonkey from the local file or from the raw GitHub URL. `QA.md` is the manual checklist for the live site; run it before a release and add a row when a feature adds visible UI.

`docs/` is the project's site on GitHub Pages (https://pdxlife.github.io/warlight-muli-script/), mainly hosting images for forum posts; `PUBLISHING.md` explains it. `docs/guide.html` is its how-to page for every feature, with setting names as the settings menu shows them: update its section when a feature is added, changed or removed. Images used in forum posts are PNG or JPG, and motion is an animated PNG made with `tools/make_apng.py`: war.app's phone app shows neither SVG nor GIF (tested), the forum can't play video, and the app shows an APNG's first frame as a still, so that frame must make sense alone. A file a forum post uses must never be renamed or deleted.

## How the script is put together

- **Source files:** `src/header.js` is the metadata block, `src/core/` holds what every area uses (`boot.js` is the startup sequence, `features.js` the feature lists), and `src/features/` has one file per area. The files are plain scripts, not ES modules: there are no imports, and all of them share one scope once joined, so a function in any file can call one in any other. The build puts `header.js`, `core/constants.js` and `core/boot.js` first, then every other file sorted by path, so a new file needs no registration. Boot runs before the other files' top-level code, so they stay independent at load time: a `var` that needs another's value belongs in the same file or in `constants.js`, and a test enforces this. New feature code goes in its area's file; add a file when it's a feature of its own. Error line numbers in the log refer to the built file.
- **Header:** `@grant none`, so the script runs in the page context. The site's own globals (`$.cookie`, `wljs_WaitDialogJS`, `CreateModal`, Bootstrap's `.modal()`) are available. Switching to any `GM_*` grant sandboxes the script and breaks these.
- **Two jQuerys:** `$` is the site's jQuery, which has the cookie plugin. `$$$` is the `@require`d jQuery 1.11.2 plus jQuery UI, used for the log dialog. DataTables is attached to `$$$`, so call it as `$$$(...).DataTable()`. Never reassign `window.$` or call `noConflict` on the site's jQuery: war.app's pages, the cookie plugin and Bootstrap depend on it.
- **Startup flow:** `DOM_ContentReady()` starts `loadPlayerData()` and runs a list of page features through `runFeatures()`. It then calls `Database.init()`, whose callback runs the menu setup, `checkVersion()` and `databaseReady()`, which is a second feature list for settings-driven features. The lists are built by `pageFeatures()`, `mainFeatures()` and `maakFeatures()`. Each feature is `{ name, section?, match?, run }` and runs in its own try/catch. Add new features as entries pointing at named top-level functions, not as inline blocks. List order is execution order. A feature with a `section` gets a switch in that section of the settings menu, next to the settings (`userscriptSettings`, each with a `section` too); `MENU_SECTIONS` lists the sections in order with their headings. Its `name` is shown to users and is the key in the stored disabled list, so don't rename it casually. The disabled list lives in the `disabledFeatures` setting and is mirrored to `localStorage` (`DISABLED_FEATURES_KEY`), because page features run before IndexedDB opens.
- **Page routing:** done with the `pageIs*()` helpers, which match the path of `location.href` on any host; `@match` decides which hosts the script runs on.
- **Domains:** nothing hard-codes the site's domain. Links are relative or built from the page (`$a.prop("href")`), page titles are trimmed with the site's own `og:site_name` (`stripSiteSuffix()`), and bookmarks saved on any host in `SITE_HOSTS` render as relative links (`siteRelativeUrl()`). warzone.com and warlight.net only redirect to war.app now, so `@match` lists war.app alone; the old domains stay in `SITE_HOSTS` for old bookmarks. If war.app moves to a new domain, add an `@match` line and add the domain to `SITE_HOSTS`, nothing else. IndexedDB and cookies are per origin, so users carry settings to a new domain with Export / Import.
- **Player data:** `loadPlayerData()` returns a jQuery promise, stored as `window.playerDataReady`. Anything that reads `WlPlayer` must wait on it. It rejects when the user is logged out.
- **Storage:** IndexedDB `TidyUpYourDashboard_v3`, wrapped by `window.Database` from `setupDatabase()`. Every method takes an optional callback and also returns a Promise; failures and callback exceptions are logged. Settings are cached at `init`, and `readIndex` on the Settings name index is served from the cache. Writes update the cache when issued, and callbacks still run asynchronously. Tables are listed in `Database.Table`; only `Database.Exports` tables are included in settings export and import. Player data is cached in the `muli_wl_player` cookie for 1 hour.
- **Third-party services:** maak.ch (proxy and API), www.warlight-mtl.com (the Multi-Template Ladder, MTL, formerly called MDL; the bare `warlight-mtl.com` host also works), communitylevels.online. Any of these can be down, so every request needs a `.fail()` handler. maak.ch and warlight-mtl.com send no CORS headers, so under `@grant none` they can only be reached through maak.ch's JSONP endpoints, which run as code on war.app. Everything that calls maak.ch is reachable only through `setupMaakFeatures()`, behind the `useMaakServices` setting (off by default), and a test enforces this. awp.wl-stats.com and custom.wl-stats.com (run by this fork's maintainer) send CORS headers for `https://war.app` and its subdomains, so the script reads their `/api/v1/` JSON directly with `fetchWlStats()` (custom's `/api/v1/ladders` has the Seasonal Ladder and its copy of the MTL), which keeps answers in `sessionStorage` (an hour by default, 10 minutes for `/api/v1/series`) and resolves a 404 with `null`. Profile boxes from these sites go through `placeProfileBox()`, which keeps them in a fixed order below the private notes. `loadCommunityData()` loads the AWP ranking and the custom series side by side for the Ladders and Community Events pages; custom's times have no zone and are UTC (`parseUtcTime()`). Prefer war.app's own pages for new data, as `fetchDashboard()` and `parseLevelPage()` do. They're same-origin, so parse them with `DOMParser`, never `$(html)`, so their scripts and images stay inert.
- **Game refresh event:** `refreshGameTable()` triggers `tuyd:gamesRefreshed` on `document` with the table selector after each refresh, including the 5-minute background check from `setupTurnAlerts()`. Hook into it rather than wrapping the refresh functions. Most other pages (tournaments, ladders, clan pages) are now drawn client-side by war.app as absolutely positioned `ujs_*` elements and have no `#MainSiteContent`. war.app also switches between these views without a page load (e.g. tournaments list → tournament), redraws them, and numbers repeated ids (`ujs_CreatorLabel_2_tmp`). So features for these views watch the page with a `MutationObserver` and re-check each time (`whileOnTournament()`), add their elements only if missing, look elements up with `ujsElement()`, and don't insert into war.app's flow (`tournamentInfoSlot()`). The Ladders panel (`setupCommunityLadders()`) follows the same rules, but sits in war.app's full-width `#UjsCanvasHolder` rather than the 600px `ujs_Viewport`, positioned under the dialog's background box (`fitCommunityLadders()`), and sizes its own scrolling to what's left of the window. Panels styled like war.app (`.tuydCommunityPanel`) take war.app's dialog, row and button art from the page by file name (`warappArt()`), so they work on any scene. Where an addition only fits at some widths, a CSS container query on the element it sits in decides, not a viewport media query: war.app re-lays out its scenes at its own pace and widths. The script targets desktop browsers: war.app's phone app can't run it and war.app sends phone browsers to `/Mobile`, so "narrow" means a narrow desktop window, not a phone. In My Games, the dashboard's clickable-rows style stretches every direct `<a>` child of a game's second cell over the cell (`.GameRow td:nth-of-type(2) > a`), so additions there go inside their own element, not as a bare link (the event badges sit in an absolutely positioned corner element, `.tuydEventBadgeCorner`). Anything clickable needs `pointer-events: auto`, since war.app's panels often have `pointer-events: none`. war.app's own Filter button (`#MyGamesFilterBtn`) re-draws My Games in place without this event; a feature that must follow every re-draw observes the table instead, pausing the observer while it changes rows, as `setupBootTimeSort()` does. A My Games row is your turn when it contains a span whose text starts with "Your turn". War.app Idle (`/Idle/Play`) is drawn the same way: its map is a canvas, but its tabs, dialogs and buttons are `ujs_*` elements. Its buttons are `<a class="ujsBtnInner" id="ujs_…_btn">` links with a jQuery click handler, so the Idle confirmations use a capturing click listener on `document` that stops the click on Cancel; its sounds are SoundManager 2 HTML audio. Idle helpers inform and ask, never play the game; testing them live means opening Idle on the maintainer's account, so only after they've closed it elsewhere, and never click map territories, Purchase or Use. After replacing rows, `refreshGameTable()` copies the fresh `#AllOpenGamesData` into the page and re-runs war.app's exported `WL_MPDashInit` (`rerunDashboardInit()`), which re-adds the My Games footer and the Open Games "Show more" row.

## Tests

`test/harness.js` builds the userscript from `src/`, parses it with acorn and evaluates individual top-level function declarations in a `vm` sandbox. Loading the whole file would run page setup. Each test passes in only the globals the function under test needs. Common ones are `$` (npm jQuery 1.11.2 bound to a jsdom window, via `createDom()` and `domGlobals()`), `log`, `Database` and `location`.

- `test/build.test.js` fails if the committed `.user.js` isn't what `src/` builds. After a merge conflict, resolve `src/` and rebuild rather than fixing the built file.
- `test/startup.test.js` checks statically that every called or feature-registered function exists. If it flags a new site or browser global, add that name to its allowlist.
- A function becomes testable once it is a **top-level `function` declaration**. Inline logic in `databaseReady()` or `DOM_ContentReady()` has to be extracted first, as was done with `setupBlacklistCounter()`.
- Values created in the sandbox come from another realm. Copy arrays with `Array.from` or a JSON round-trip before using `deepStrictEqual`.
- jsdom has no layout. The harness patches `offsetWidth` so jQuery's `:visible` respects `display: none`.

## Working on changes

- State assumptions before building on them. If a request has more than one reasonable reading, ask rather than pick one silently.
- Change only what the task needs: no extra features, settings or abstractions, and no tidying of nearby code, comments or formatting. Mention unrelated problems instead of fixing them. The rebuilt `.user.js` and the docs this file requires (`QA.md`, `docs/guide.html`, version lines) count as part of the change.
- Say how a change will be verified before making it. Reproduce a logic bug with a failing test first. jsdom has no layout, so layout and live-site behaviour are checked through `QA.md`.

## Conventions

- When bumping the version, update `@version` in `src/header.js`, the `GM_info` fallback in `src/core/constants.js`, the version line in `README.md`, and the version next to the title in `docs/index.html` together. A test checks that they match.
- `@downloadURL` and `@updateURL` must point at this repo's raw file, not Greasy Fork. Otherwise upstream releases overwrite this fork.
- Escape third-party and user-supplied strings with `htmlEscape()` before putting them into HTML. URLs from outside (API data, bookmarks) go through `htmlEscape(safeUrl(url))`; `safeUrl` allows only `http(s)://` and same-site `/` paths. `test/security.test.js` covers each renderer with an injection payload, so add a case there when adding a new one.
- Every `@require` must carry a `#sha256-` hash. A test enforces this.
- `SCRIPT_URL` must stay equal to `@downloadURL` (a test checks it): the update notice reads the version from it, and the corner label's update link opens it.
- `ROADMAP.md` tracks planned work. Tick items off there when they land.
